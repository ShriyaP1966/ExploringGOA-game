# ExploringGOA

Browser game: a 3-day summer trip to Goa. The player controls everything by typing or speaking natural sentences.

## Game scope
- 5 Goa locations, 3 quests, 4 random events
- Stats: money, energy, time, XP, 3 levels
- Inventory, discoveries, memories
- Rule-based command parser — **no outside AI or API calls**
- Always-visible voice panel (browser speech recognition)
- Final adventure score and a personalized recap screen

## Stack
Vite + React + TypeScript, Vitest for unit tests.

## Layout (`src/`)
- `components/` — React UI. Renders state and dispatches player input; never mutates game state.
- `engine/` — **all game rules** (state transitions, costs, quests, events, scoring). Pure functions, unit-tested.
- `state/` — store wiring that holds engine state and calls engine functions.
- `data/` — static content (locations, quests, events, items).
- `parser/` — turns sentences into structured commands. Returns intents only; never changes state.
- `hooks/` — React hooks (e.g. speech input, store access).
- `styles/` — CSS.
- `types/` — shared TypeScript types.

## State flow
- One `GameState` (`src/types/game.ts`), held by `GameProvider` (`src/state/`) via `useReducer`.
- Components read with `useGameState()` and send `GameAction`s with `useGameDispatch()` (`src/hooks/useGame.ts`).
- `gameReducer` (`src/engine/reducer.ts`) routes each action to a pure rule function in `src/engine/` — the only place state changes.
- Rejected actions set `state.notice` (e.g. not enough money); the reducer clears it on the next action.
- Limits and starting values live in `src/engine/config.ts` (including `TRAVEL_RULES` and `DAY_END_MINUTE`).
- Engine "check" functions (e.g. `quoteTravel`, `checkScooterRental`) validate without changing state; the UI uses them to show options and refusal reasons, and the matching action re-runs the same check.
- Game phases (`state.phase`): `day-intro` → `playing` → `day-summary` → next day's intro, or `ended`. The reducer ignores gameplay actions outside `playing`, and ends the day automatically at 10 PM or after the Day 3 sunset. Per-day rules (regions, scooters, finale) live in `src/data/days.ts`.
- All XP goes through `addXp` (engine/player.ts), which sets `state.levelUp` on a new level. XP amounts are in `XP_REWARDS`, level perks in `LEVEL_PERKS` (config.ts); level titles in `src/data/levels.ts`. Discovery always goes through `markDiscovered`.
- Memories are never handed out directly. Systems report what happened with `recordMoment(state, moment)` (engine/memories.ts); story memories in `src/data/memories.ts` declare the triggers they wait for. The future events and quests systems must call `recordMoment` with `{ type: 'event' }` / `{ type: 'quest-complete' }`.
- Quests are data (`src/data/quests.ts`) built from `QuestCondition`s; `updateQuests` (engine/quests.ts) runs after every action while playing and starts, advances (in step order), completes and fails them, writing `state.questUpdates`. Add a quest by adding data, not engine code. A quest's `constraint` must hold the whole time (checked before steps); `day-ending` is only true in the reducer's final quest check before any day closes, so end-of-day failures show on that day's summary. Trips are logged in `state.tripLog`. Rewards go through `addXp`/`addItem` and memories through a `quest-complete` moment.
- The Day 3 finale (engine/finale.ts) scores the ending from real state when the final sunset is watched (`state.finalSunset`); the Final Sunset quest's reward adds that bonus to XP and `state.scoreBonuses`, then sets `ending`. Watching needs no money or energy, so the trip can always end.
- Random events are data (`src/data/events.ts`) with state conditions, a probability and a cooldown; `maybeTriggerEvent` (engine/events.ts) runs after a successful trip or activity and fires at most one. While `state.activeEvent` is set the reducer only accepts `CHOOSE_EVENT_OPTION` (and reset), and the day cannot end. Resolving logs to `state.eventLog` and reports an `event` moment (with `choiceId`) for memories.
- Commands: the voice panel (`components/voice/VoicePanel.tsx`) calls `parseCommand` (`src/parser/index.ts`, the rule-based parser: no AI, no API) and dispatches one `COMMAND` action. Parser vocabulary lives in `src/parser/lexicon.ts`, location nicknames in each location's `aliases`, and an activity's own words ("parasailing", "shells") in its `keywords`; add words there rather than in code. `src/parser/dictation.test.ts` is a sweep of realistic dictated sentences checked through parser and mapper: add a case for every new phrasing. `mapCommand` (engine/actionMapper.ts) turns it into ordinary actions, an answer, or a refusal; it reads state and may use engine check functions (via engine/recommend.ts) but never changes state. The reducer runs each action through every rule and records its own result in `state.lastAction` (ok + reason, judged before quests/events react); `recordCommand` stores the outcome (success / refused / answered / not-understood), the reason and the real before/after changes in `state.commandLog` (last 5). The parser never changes state. Every refusal must give a human-readable reason; add a test in engine/commandFlow.test.ts for any new rule a command could try to skip.
- Intents are scored, not matched in order: `scoreIntents` (`src/parser/intents.ts`) adds weights from keywords, extracted entities and the read-only `ParseContext` (current place, pending question, scooter). Confidence below `MIN_CONFIDENCE` (0.45) means `unknown`. When adding phrases, add a test for any intent they could be confused with.
- Recommendations (`recommend` in engine/recommend.ts) score places on mood ratings, travel + activity cost, energy, distance and time of day; hard limits are real money, the player's own limit, energy and the travel rules (ruled-out places keep their reason). Wish-based requests answer with a suggestion and wait for "yes". Meals are activities with `meal: true`. The player's stated money is never trusted over `state.player.money`; a mismatch becomes a note in the command record.
- The voice input must stay focused for dictation (Wispr Flow): don't add `autoFocus` elsewhere. Overlays stop above the panel via `--voice-panel-height`.
- Chance rolls use the seeded `nextRandom(state.rngSeed)` (engine/random.ts) and store the next seed, so rules stay pure. Never call `Math.random()` inside game rules; tests pass a fixed seed to `createInitialState(seed)`.
- Never add a CSS `@import` before the imported file exists — Vite's dev server caches the failed lookup.
- Developer panel (`components/dev/DevPanel.tsx`): hidden, rendered only after Ctrl+Shift+D (Esc or the shortcut closes it). It only sends ordinary `GameAction`s through the reducer; multi-step tools are planned by pure functions in engine/devTools.ts (`planJump` = END_DAY → CONTINUE_AFTER_SUMMARY → BEGIN_DAY → ADVANCE_TIME, resetting first if the target is in the past). `RECEIVE_MONEY` and `FORCE_EVENT` exist only for it.
- Autosave: `GameProvider autosave` writes `serializeGame(state)` to local storage (`state/autosave.ts`, key `exploringgoa.save`) after every state change, but only once you leave the title screen. The title screen offers Continue when `parseSave` accepts the save (versioned with `SAVE_VERSION`; damaged or impossible saves are ignored; missing fields get starting values) and loads it with `LOAD_GAME`. Bump `SAVE_VERSION` when the state shape changes incompatibly.
- Conversation layer (`engine/conversation.ts`, read-only helpers used by the mapper): while an event waits, spoken text is matched to the closest choice (`matchEventChoice`: choice `keywords`, negation like "don't want to pay", money wishes like "no money"; ambiguous → "did you mean…", nothing → polite refusal listing choices). A pending suggestion (last command's `suggestion`) is confirmed by yes, dropped by no/cancel, and replaced by any other command; a local's `pendingHelp` lapses (auto `DECLINE_HELP`) when the player acts on something else. Unknown/low-confidence input → `not-understood` with `didNotCatch` (2–3 `situationalSuggestions`, on every screen); `help` → `helpText`. Never-crash: `parseCommand` caps input at `MAX_COMMAND_LENGTH` (500) and catches errors; the reducer catches mapper errors; `VoicePanelBoundary` wraps the voice panel.
- The ending: when the trip ends (Final Sunset quest completes, or Day 3 closes) `endDay` goes straight to phase `ended`, still recording the last day's summary, and `DayOverlay` shows the My Goa Summer recap (`components/recap/MyGoaSummer.tsx`). `adventureScore` (engine/score.ts) is pure and uses only real tracked values (days, places, quests, money spent, km, memories, XP, level) plus the under-budget bonus and `state.scoreBonuses`; weights, caps and rank thresholds live in `SCORE_RULES` (config.ts). `tripRecap` (engine/recap.ts) picks the favourite place and best memory and writes the personal highlights. Play again is `RESET_GAME`.
- Visuals: tokens (colours, gradients `--grad-*`, glass, layered shadows) live in styles/theme.css; use them rather than new literals. The sky is one pure function, `skyLook(minuteOfDay)` (components/scene/sky.ts, presentation only), shared by the scenes, the HUD dial and the page background (GameScreen sets `--sky-*` variables). Each location's scene is a layered SVG component in components/scene/scenes.tsx, registered in scene/registry.ts and drawn in a 960×480 frame (`frame.ts`; horizon `HORIZON`); colour land with `lit()` (follows the light) or `far()` (haze), add night lights with `Lamp`/`Window`/`FairyLights`. `SceneArt` shows at least 380 units of height and mirrors the edges sideways on wide stages, so keep landmarks below y≈100 and let shapes run edge to edge. No external images; animations must respect `prefers-reduced-motion`. The HUD is components/layout/TopBar.tsx + styles/hud.css.
- Feedback layer (display only): `components/feedback/changes.ts` compares the previous and next state (`statDeltas`, `toastsFor`; `isRewind` ignores resets and loads) and `useChangeFeed` turns that into short-lived items: floating numbers on the HUD chips (`StatFloats`) and toasts (`ToastLayer`) for discoveries, quest news, XP, level-ups and memories. Toasts replaced the old level-up/quest/memory banners; the notice and local-help offer stay in the stage. Memories render with `MemoryCard` (a Polaroid whose photo is `SceneArt` at the memory's place and minute, `still`), used in the memories panel and on the final screen. Every `SceneArt` gets its own SVG id prefix via `SceneIdContext`; use `useSceneIds()` for any new gradient. Motion lives in styles/finish.css (transform/opacity only) and must have a reduced-motion rule.
- First impression: the title screen (`TitleScreen.tsx`) shows the `Logo` (SVG emblem + "Exploring Goa" wordmark, `GAME_CONFIG.displayName`/`motto`), Start adventure (asks again before replacing a save) and Continue (disabled without a save). How to play (`help/HowToPlay.tsx`) opens from the title and the HUD "?", stops above the voice panel and never takes focus; its example phrases live in `data/howToPlay.ts` (each is tested to parse) and clicking one fills the input via `fillVoiceInput`. Voice focus: the input refocuses after any click on a non-text element, after Escape, when focus would land on nothing, and on screen/popup/command changes; text fields (dev panel) keep their focus. Layout breakpoints live in styles/first.css: ≤1180px narrower side panel and icon-only HUD brand, ≤860px one scrolling column with a compact two-column voice panel, ≤560px single-column voice results.
- Time and items by voice: asking for an activity that opens later today (sunsets, the evening festival) waits for it (`ADVANCE_TIME` then `DO_ACTIVITY`) if it will be possible then, else refuses with the real reason; "wait…" phrases pass time (an hour, or until the evening). On the finale day "watch the sunset" falls back to the free `WATCH_FINAL_SUNSET` whenever the local sunset activity can't happen, so the trip can always end. The `use-item` intent matches items by name or `aliases` (data/items.ts). Game text uses `{startMoney}`, `{tripDays}`, `{placeCount}` placeholders filled by `fillTemplate` (components/format.ts) instead of hardcoded numbers.
- `src/engine/playthrough.test.ts` plays whole three-day trips by voice for four kinds of player over 25 seeds (quests, events, stats consistency, money lasting, the trip always ending). Run it after any balance change; levels are Explorer 150 XP and Local Legend 450 XP (data/levels.ts), and tests read thresholds from `levelInfo`, never literals.

## Commands
- `npm run dev` — dev server
- `npm run typecheck` — TypeScript check (`tsc -b`)
- `npm test` — Vitest, single run. Run it from `D:\ExploringGOA` (capital drive letter): started from `d:\ExploringGOA`, Vitest on Windows fails every file with "Cannot read properties of undefined (reading 'config')".
- `npm run build` — production build (base path `/`; set `BASE_PATH=/<repo>/` for a GitHub Pages project site — in Git Bash also set `MSYS_NO_PATHCONV=1`, or the path gets rewritten)
- Deploy: `.github/workflows/deploy.yml` runs typecheck, lint, tests and the build with the right `BASE_PATH`, then publishes `dist/` to GitHub Pages on every push to `main` (Pages source must be "GitHub Actions"). The developer panel only exists in dev builds or with `?dev` in the URL.

## Working rules (follow in every session)
1. Always inspect existing files before editing.
2. Never rewrite working code — make targeted changes.
3. Build one system at a time.
4. Keep all game rules inside `src/engine`. The parser and the UI can never change state directly; they only produce commands that the engine applies.
5. After every change, run `npm run typecheck` and `npm test`, and fix anything that breaks before moving on.
